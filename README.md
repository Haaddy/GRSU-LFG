# LFG — Database

Структура базы данных хранится в виде SQL-миграций.
Миграции нужны для того, чтобы все участники команды могли создать одинаковую структуру базы данных у себя локально.

## Структура папки database

```text
database/
├── migrations/
│   ├── 001_create_users.sql
│   ├── 002_create_events.sql
│   ├── 003_create_teams.sql
│   └── ...
└── seed.sql (это потом будут тестовые данные в бд покачто этого нет так что забейте)
```

### `migrations/`

В этой папке находятся SQL-файлы, которые создают и изменяют структуру базы данных.

Миграции необходимо выполнять **по порядку**.

### `seed.sql`

Содержит тестовые данные для разработки.

`seed.sql` не изменяет структуру базы данных.

пока не создавать потом будем тестовые данные подгрузим

# Установка базы данных

## 1. Установить PostgreSQL

У каждого PostgreSQL должен быть установлен локально.

## 2. Создать базу данных

Создайте базу данных с названием:

```text
lfg
```

Например, через **pgAdmin**:

```text
Servers

    └── Databases
        └── Create → Database
```

Название базы:

```text
lfg
```

# Создание таблиц

После создания базы данных необходимо выполнить миграции.

Откройте в pgAdmin:

```text
Databases → lfg → Query Tool
```

После этого откройте первый файл:

```text
database/migrations/001_create_users.sql
```

Скопируйте SQL-код в Query Tool и выполните его.

После этого повторите для следующих миграций(**по порядку** делать)


После выполнения всех миграций структура базы данных будет создана.

---


# Как изменить структуру базы данных

Если необходимо изменить существующую таблицу, **не изменяйте уже созданную миграцию**.

Например, у нас уже есть:

```text
001_create_users.sql
002_create_events.sql
```

И нам понадобилось добавить в `events` поле `location`.

Не нужно менять:

```text
002_create_events.sql
```

Вместо этого создайте новую миграцию:

```text
003_add_event_location.sql
```

В ней:

```sql
ALTER TABLE events
ADD COLUMN location VARCHAR(255);
```

После этого:

1. сохраните файл;
2. добавьте его в Git;
3. сообщите команде, что появилась новая миграция.

Другие разработчики выполняют:

```text
003_add_event_location.sql
```

и получают обновлённую структуру БД.

---

# Главное правило миграций

### Не изменяем старые миграции

Например, уже существует:

```text
001_create_users.sql
002_create_events.sql
003_create_teams.sql
```

Если `003_create_teams.sql` уже был отправлен в Git и кто-то из команды его выполнил, **не нужно редактировать этот файл**.

Если требуется изменение — создаём следующий файл:

```text
004_change_teams.sql
```

Например:

```sql
ALTER TABLE teams
ADD COLUMN description TEXT;
```

Получается история изменений:

```text
001 → создание users
002 → создание events
003 → создание teams
004 → изменение teams
005 → изменение events
...
```

Это позволяет всем разработчикам понимать, как изменялась база данных.

---

# Если я добавил новую миграцию

Допустим, вы добавили:

```text
004_add_event_category.sql
```

После этого:

```bash
git add database/migrations/004_add_event_category.sql
git commit -m "Add event category migration"
git push
```

Другой разработчик получает изменения через:

```bash
git pull
```

После этого ему необходимо выполнить новую миграцию:

```text
004_add_event_category.sql
```

После выполнения его локальная база будет соответствовать текущей структуре проекта.

# Миграции и Git

В Git необходимо хранить:

```text
database/
├── migrations/
│   ├── 001_create_users.sql
│   ├── 002_create_events.sql
│   ├── 003_create_teams.sql
│   └── ...
└── seed.sql
```

В Git **не нужно хранить саму PostgreSQL-базу данных или файлы её внутреннего хранилища**.

Мы храним SQL, из которого можно восстановить структуру базы.

# Важные правила для команды

1. **Не изменяем старые миграции**, которые уже были отправлены в Git.
2. Любое изменение структуры БД оформляем новой миграцией.
3. Миграции выполняем по порядку.
4. `seed.sql` используется для тестовых данных.
5. Реальные пароли в БД хранятся только в виде хэшей.
6. Не добавляем локальные данные и пароли в Git.
7. Не добавляем внутренние файлы PostgreSQL в Git.
8. Перед началом работы желательно выполнить:

```bash
git pull
```

чтобы получить последние миграции.

# Основные API-маршруты

Все маршруты backend используют префикс `/api`.

Для защищённых маршрутов требуется заголовок:

```http
Authorization: Bearer <JWT-токен>
```

## Авторизация

| Метод | Маршрут | Назначение | Доступ |
|---|---|---|---|
| `POST` | `/api/auth/register` | Регистрация пользователя | Публичный |
| `POST` | `/api/auth/login` | Вход пользователя | Публичный |
| `POST` | `/api/auth/logout` | Удалить cookie авторизации | Публичный |

## Профиль и dashboard

| Метод | Маршрут | Назначение | Доступ |
|---|---|---|---|
| `GET` | `/api/profile` | Получить профиль текущего пользователя | Авторизованный |
| `PATCH` | `/api/profile` | Изменить профиль текущего пользователя | Авторизованный |
| `GET` | `/api/profile/statistics` | Получить статистику пользователя | Авторизованный |
| `GET` | `/api/dashboard` | Получить данные dashboard пользователя | Авторизованный |

## Мероприятия

| Метод | Маршрут | Назначение | Доступ |
|---|---|---|---|
| `GET` | `/api/events` | Получить список мероприятий | Публичный |
| `POST` | `/api/events` | Создать мероприятие | Авторизованный |
| `GET` | `/api/events/{eventId}` | Получить одно мероприятие | Публичный |
| `PATCH` | `/api/events/{eventId}` | Изменить мероприятие | Организатор |
| `DELETE` | `/api/events/{eventId}` | Удалить мероприятие | Организатор |
| `GET` | `/api/events/{eventId}/statistics` | Получить статистику мероприятия | Авторизованный |

Список мероприятий может поддерживать query-параметры:

```text
GET /api/events?status=upcoming
GET /api/events?search=hackathon
GET /api/events?from=2026-10-01&to=2026-12-31
GET /api/events?need_team=true
GET /api/events?page=1&limit=20
```

Основные query-параметры:

```text
status       — upcoming, active или completed
search       — поиск по названию
from, to     — фильтрация по периоду
need_team    — мероприятия с командами или без команд
page, limit  — пагинация
sort, order  — сортировка
```

## Параметры маршрутов

Части URL в фигурных скобках являются динамическими параметрами:

```text
/api/events/{eventId}
/api/teams/{teamId}/members/{userId}
```

Например, запрос:

```text
GET /api/events/25
```

передаст в обработчик:

```php
[
    'route' => [
        'eventId' => 25
    ],
    'query' => [],
    'auth' => []
]
```

Параметры `query` берутся из части URL после `?`, а данные `auth`
добавляются middleware после успешной проверки JWT.
